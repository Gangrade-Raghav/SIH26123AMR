## 1. Executive Summary & Goal

Milestones M0, M1, and M2 successfully built and empirically validated the decentralized AMR fleet simulation across 1, 2, 5, and 10 robots in ROS 2 Jazzy and Gazebo Harmonic.

However, the raw default simulation presentation is visually basic: the warehouse is an unadorned grey plane, lighting is harsh, camera perspective is off-center, robots appear as plain monolithic blocks, and there is no dedicated observability dashboard for live demonstration.

The objective of **Milestone M2.5** is to create an executive, hackathon-ready demonstration layer that presents NRDAS as a premier research-grade multi-robot fleet coordination system while **strictly preserving** all existing robot physics, collision models, kinematics, sensor streams, ROS 2 interfaces, and simulation semantics.

## 2. Requirements & Boundary Invariants

### 2.1. Strict Non-Regression Rules
- **No Physics Tampering**: Do not alter mass, wheel radius ($0.10\,\text{m}$), wheel separation ($0.45\,\text{m}$), chassis collision boxes ($0.65 \times 0.45 \times 0.18\,\text{m}$), or caster friction coefficients.
- **No Interface Drift**: Preserve topic signatures (`/${robot_name}/cmd_vel`, `/${robot_name}/odom`, `/${robot_name}/scan`, `/${robot_name}/tf`).
- **No Fabricated Telemetry**: The dashboard and observability components must read ground-truth ROS 2 topics and system diagnostics. Unimplemented features (M3 task allocator, M6 MAPF planner, M8 deadlock monitor) must be marked as `N/A - Pending Milestone MX`.
- **Lightweight Geometry**: All visual markers, striping, and rack details must use static primitives or lightweight visual geometry to ensure zero degradation of the simulation Real-Time Factor (RTF).

## 3. Detailed Component Plan

### 3.1. World & Environment Overhaul (`warehouse_small.sdf`)
The environment will be upgraded from a generic box to an authentic smart logistics warehouse:
1. **Industrial Flooring**:
   - Slate-grey epoxy finish (`#22262c`) with ambient/diffuse/specular shading.
   - Visual boundary warning kickplates along all walls.
2. **Floor Markings & Traffic Lanes**:
   - High-contrast safety yellow (`#f1c40f`) boundary striping defining:
     - **Corridor 1 (Western Staging Aisle)**: $x \in [1.0, 3.0]$
     - **Corridor 2 (Central Arterial Highway)**: $x \in [7.0, 9.0]$
     - **Corridor 3 (Eastern Logistics Aisle)**: $x \in [13.0, 15.0]$
     - **Cross-Aisles (North & South Transits)**: Connecting all corridors.
   - Directional transit arrows and safety crosswalk stripes.
3. **Dedicated Operational Zones**:
   - **4 Pickup Stations**: Located at $(2, 2)$, $(2, 13)$, $(13, 2)$, and $(13, 13)$ with industrial cyan/blue pads (`#2980b9`) and boundary collars.
   - **Central Fulfillment & Sorting Hub**: Centered at $(7.5, 7.5)$ with logistics emerald green pads (`#27ae60`).
   - **4 Charging & Maintenance Bays**: Designated parking pads with amber/hazard stripes (`#d35400`).
4. **Structured Multi-Tier Industrial Storage Racks**:
   - Replace basic solid boxes at $(4.5, 5.5)$, $(4.5, 10.5)$, $(11.5, 5.5)$, $(11.5, 10.5)$ with realistic dual-tier warehouse racking:
     - Deep industrial blue upright structural columns (`#2c3e50`).
     - Safety orange cross-beams (`#e67e22`).
     - Pallet cargo totes on shelves (static boxes, zero physics load).
     - Physical collision boundaries strictly match existing dimensions $(1.2\,\text{m} \times 3.0\,\text{m} \times 2.0\,\text{m})$ to maintain $100\%$ compatibility with `config/maps/warehouse_grid_small.yaml`.

### 3.2. Deterministic Presentation Camera (`warehouse_small.sdf`)
Incorporate Gazebo Harmonic GUI camera settings directly into the world SDF:
- Plugin: `gz-sim-scene-broadcaster-system` and `<gui>` configuration with `GzScene3D`.
- Fixed Demonstration Camera Pose:
  $$\text{Pose} = (8.0, -3.5, 16.5, 0.0, 0.92, 1.5708)$$
  - Pitch: $\approx 53^\circ$ downward.
  - Yaw: $90^\circ$ (looking straight north along warehouse aisles).
  - Center of View: $(8.0, 8.0)$ — the geometric center of the warehouse.
  - Framing: Captures the entire $16 \times 16\,\text{m}$ active floor with optimal screen margins and zero manual repositioning needed.

### 3.3. Robot Visual & Identification Enhancements (`amr_fleet_description`)
Upgrade the AMR model visual representation:
1. **Chassis Aesthetic**:
   - Dual-tone finish: matte charcoal-slate lower chassis (`#1e2229`) with chamfered high-visibility safety orange top shell (`#e65c00`).
2. **LiDAR Housing**:
   - Two-tier realistic sensor tower: cylindrical dark-matte mount base + metallic sensor rotor with an optical window ring.
3. **Wheel Assembly**:
   - Distinct dark rubber tread (`#15171a`) with metallic alloy hub rims (`#a6b0b8`).
4. **Visual Status Indicator**:
   - Active status beacon ring on the top deck with emissive green glow (`<emissive>0.0 0.8 0.3 1.0</emissive>`), visually communicating active autonomous state.
5. **Unique Robot Identifier Badge**:
   - High-contrast identification plate prominently positioned on top of the robot chassis with distinct contrast trim, enabling immediate visual tracking of individual AMRs during fleet operations.

### 3.4. Deterministic Multi-Robot Demonstration Scenario
Provide a demonstration launcher and coordinator script:
- **Files**: `src/amr_fleet_bringup/launch/demo_fleet.launch.py` and `scripts/run_fleet_demo.py`.
- **Fleet Size**: 5 AMRs (or configurable up to 10).
- **Trajectory Script**:
  - Deterministic multi-stage motion:
    - Phase 1: AMRs in western corridor (`amr_0`, `amr_1`) execute staging maneuvers toward pickup bays.
    - Phase 2: `amr_2` transits down the Central Arterial Highway toward the fulfillment hub.
    - Phase 3: Coordinated counter-flow passing and return loops using standard `/cmd_vel` inputs.
  - Smooth velocity ramps ensuring kinematics limits are respected.
  - Self-looping demo capability for unattended presentation runs.

### 3.5. Decoupled Fleet Observability Suite
A dashboard architecture built entirely on ground truth:
```
+-------------------------------------------------------------+
|                     AMR FLEET MONITOR                       |
+-------------------------------------------------------------+
| 1. ROS 2 Node (amr_fleet_monitor):                          |
|    - Subscribes to /amr_*/odom, /amr_*/scan, /amr_*/cmd_vel |
|    - Queries ROS 2 Graph (Node & Topic discovery)           |
|    - Inspects system health (/proc/loadavg, memory)         |
|                                                             |
| 2. Zero-Dependency HTTP & REST Server (localhost:8080):     |
|    - Serves dark-themed modern executive dashboard UI       |
|    - Streams real-time JSON updates every 500ms             |
|                                                             |
| 3. Rich Terminal TUI Mode:                                  |
|    - Live multi-panel terminal dashboard via `rich`         |
+-------------------------------------------------------------+
```
The dashboard exposes:
- **FLEET**: Active robot count, per-robot poses $(x, y, \theta)$, linear/angular velocities, and state (`ACTIVE` / `IDLE`).
- **TASKS**: Pending / Active / Completed counters (marked `[Pending M3 Task Engine]`).
- **NETWORK**: Node count, topic rates (Hz), DDS discovery state.
- **PERFORMANCE**: Real-Time Factor (RTF), Host CPU%, Host RAM%, MAPF Latency (`[Pending M6 PIBT]`).
- **SAFETY**: E-Stop status (`NORMAL`), Sensor clearance (`CLEAR`), Deadlock status (`[Pending M8 WFG]`).
