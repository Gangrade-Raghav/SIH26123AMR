### 3.2 Precise Task Accounting & Invariant Consistency

Task accounting is strictly defined and enforced by the state machine in `amr_fleet_core.task_model.TaskLifecycleState`:

1. **`generated_tasks` ($N_{\text{generated}} = 15$)**: The total set of task definitions loaded from `workload_medium_priority.yaml` into `amr_task_manager` at mission launch.
2. **`assigned_tasks` ($N_{\text{assigned}}$)**: Tasks that have won an auction round and transitioned from `PENDING` to `ASSIGNED` (or subsequent active states). In the tested runs, 14 or 15 tasks were assigned across AMR bundles.
3. **`completed_tasks` ($N_{\text{completed}}$)**: Tasks confirmed in state `COMPLETED` by `amr_task_manager` upon verified physical AMR odometry arrival within $0.50\text{ m}$ of the assigned dropoff location, accompanied by a verified event on `/tasks/events`.
4. **`failed_tasks` ($N_{\text{failed}}$)**: Tasks that transitioned to `FAILED` (e.g. deadline expiration or unrecoverable abort). Across all tested profiles, $N_{\text{failed}} = 0$.
5. **`remaining_tasks` ($N_{\text{remaining}}$)**: Tasks that have not reached terminal completion:
   $$T_{\text{remaining}} = T_{\text{generated}} \setminus T_{\text{completed}}, \quad N_{\text{remaining}} = N_{\text{generated}} - N_{\text{completed}}$$
   In all runs, $N_{\text{completed}} + N_{\text{remaining}} \equiv N_{\text{generated}} = 15$.

**Double-Counting Prevention**:
Tasks exist in a strictly partition-based state machine where states are mutually exclusive:
$$\text{Task Pool} = \text{PENDING} \uplus \text{ASSIGNED} \uplus \text{IN\_PROGRESS} \uplus \text{COMPLETED} \uplus \text{FAILED} \uplus \text{CANCELLED}$$
State transitions are serialized and managed atomically by `TaskManagerNode._handle_status_update()`. Duplicate updates for tasks already in a target state are discarded, guaranteeing that no task can be double-counted.

1. **Genuine Event-Derived Results**:

   - The warehouse grid requires navigating $\approx 10.5\text{ m}$ around racks and obstacles. At the robot's safe cruise velocity of $0.25\text{ m/s}$ (with rotational deceleration at turns), transit requires $\approx 50\text{ s}$.
   - Consequently, within a bounded $55.0\text{ s}$ horizon, an AMR can physically complete at most **one** full pickup-and-dropoff cycle.
4. **No Overclaiming of Continuous Throughput Curves**:
   - Because of the bounded $55.0\text{ s}$ horizon and discrete single-task completion dynamics, throughput manifests as a discrete step function ($1.09\text{ tasks/min}$ for completion at $\sim 50\text{ s}$ vs $0.00\text{ tasks/min}$ for remaining in transit) rather than a smooth, continuous degradation curve.

### 3.4 Audit of Live Gazebo CBBA Convergence

1. **Measurement Definition (`gazebo_cbba_convergence_observed_ms`)**:
   - **Start Condition**: Mission start ($t_{\text{mission\_start}}$), when task list is published and CBBA bundle construction begins.
   - **Convergence Condition**: The earliest elapsed time $t - t_{\text{mission\_start}}$ at which **all participating AMR nodes** report `is_converged == True` on their respective `/{r_id}/bundle` topics.
   - **Node-Level Convergence Logic**: In `cbba_node.py`, an individual robot marks itself converged when:
     1. No new tasks were added to its bundle during the round (`added == 0`);
     2. No conflict-resolution changes occurred to its winning bids table for $\ge 3$ consecutive consensus rounds (`self.consecutive_stable_rounds >= self.stable_thresh`);
     3. The robot has constructed a non-empty bundle (`len(bundle) > 0`).
2. **Participating Robots & Bundle States**:
   - 5 physical AMRs (`amr_0` through `amr_4`).
   - Initial State: Bundles are empty ($|\text{bundle}| = 0$).
   - Post-Convergence State: In connected profiles, AMRs converge on mutually disjoint bundles of up to 3 tasks each (e.g. `amr_0`: `task_med_0006`, `task_med_0004`, `task_med_0010`), totaling 14-15 tasks across the fleet.
3. **Consensus Scaling**:
   - Convergence duration scaled directly with transport latency: $1.65\text{ s}$ (`NORMAL`) $\to 5.59\text{ s}$ (`LOW_LATENCY`, $100\text{ ms}$) $\to 11.27\text{ s}$ (`HIGH_LATENCY`, $400\text{ ms}$).

### 3.5 Detailed Audit of Network Partition (`PARTITION`)

1. **Proof of Physical Isolation**:
   - Under `PARTITION`, the fleet is divided into Sub-fleet A (`amr_0`, `amr_1`, `amr_2`) and Sub-fleet B (`amr_3`, `amr_4`).
   - In `CommunicationImpairmentModel.is_partitioned(sender, receiver)`:
     ```python
     sender_isolated = sender_id in {'amr_3', 'amr_4'}
     receiver_isolated = receiver_id in {'amr_3', 'amr_4'}
     return sender_isolated != receiver_isolated
     ```
   - For any packet attempting to cross between Sub-fleet A and Sub-fleet B, the action is unconditionally `DROP` with `DropReason.PARTITION`.
   - **Channel Combinatorics**:
     - Intra-partition directed pairs: $3 \times 2 = 6$ (A) $+ 2 \times 1 = 2$ (B) $= 8\text{ channels}$.
     - Cross-partition directed pairs: $3 \times 2 = 6$ (A $\to$ B) $+ 2 \times 3 = 6$ (B $\to$ A) $= 12\text{ channels}$.
     - Expected drop fraction: $\frac{12}{20} = 60.0\%$.
   - **Empirical Validation**:
     - Packets sent: $253,100$.
     - Packets dropped by partition filter: exactly **$151,860$** ($60.0\%$).
     - Packets delivered (intra-partition only): **$101,240$** ($40.0\%$).
     - Zero cross-partition packets were delivered.
2. **Explanation of "Convergence" Under Partition**:
   - In `gazebo_m7_results.json`, all 5 AMRs reported `is_converged == True` at $1.60\text{ s}$.
   - **Scientific Clarification**: This represents **Intra-Partition Sub-fleet Bundle Stabilization**, NOT **Global Fleet Consensus**.
   - Because no cross-partition bids ever cross the partition boundary, Sub-fleet A resolves conflicts only among `{amr_0, amr_1, amr_2}`, and Sub-fleet B resolves conflicts only among `{amr_3, amr_4}`.
   - Both sub-fleets quickly exhaust internal conflicts and stabilize their local bundles independently. They have **no global agreement**; in fact, robots in separate partitions can unknowingly assign the same task to themselves because conflicting bids are dropped.
   - `gazebo_m7_results.json` has been updated with:
     ```json
     "convergence_type": "intra_partition_subfleet_stabilization",
     "global_consensus_achieved": false
     ```
