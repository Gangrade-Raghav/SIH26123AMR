## 1. Executive Summary

Milestone M2 transforms the single-AMR Gazebo Harmonic simulation foundation established in M1 into a scalable, genuinely parameterized multi-AMR simulation platform. Without modifying or duplicating the core robot model, controllers, or physics definitions, the fleet architecture supports dynamic scaling from 1 to 10 robots across isolated ROS 2 namespaces.

Every robot is instantiated with:
- Dedicated ROS 2 namespace (`/amr_0`, `/amr_1`, ..., `/amr_N-1`).
- Cleanly isolated command velocity subscribers (`/<robot_name>/cmd_vel`).
- Independent odometry publishers (`/<robot_name>/odom`).
- Independent planar LiDAR pointcloud publishers (`/<robot_name>/scan`) with namespaced sensor optical frames (`<robot_name>/laser_frame`).
- Fully isolated coordinate transform trees (`<robot_name>/odom` -> `<robot_name>/base_footprint` -> `<robot_name>/base_link` -> links).
- Zero inter-robot cross-talk or node name collisions in ROS 2 or Gazebo Harmonic.

Validation was conducted across 2-robot, 5-robot, and 10-robot fleet sizes in Gazebo Harmonic with the DART physics engine. All 45 automated tests passed (100% pass rate).

## 7. Namespace, TF, and Node Isolation Analysis

### 7.1 Topic Namespace Topology
```text
Root Topics:
 ├── /clock               (rosgraph_msgs/msg/Clock) - Common simulation time
 ├── /tf                  (tf2_msgs/msg/TFMessage) - Dynamic coordinate transforms
 └── /tf_static           (tf2_msgs/msg/TFMessage) - Static geometric transforms

Namespaced Topics (for robot i ∈ [0 .. N-1]):
 ├── /amr_{i}/cmd_vel     (geometry_msgs/msg/Twist) - Bidirectional diff drive command
 ├── /amr_{i}/odom        (nav_msgs/msg/Odometry) - Kinematic odometry
 ├── /amr_{i}/scan        (sensor_msgs/msg/LaserScan) - Planar 2D LiDAR ray returns
 ├── /amr_{i}/joint_states (sensor_msgs/msg/JointState) - Wheel encoder positions
 └── /amr_{i}/robot_description (std_msgs/msg/String) - Parameterized robot model
```

### 7.2 TF Frame Isolation Architecture
In a multi-robot setup, having a monolithic unnamespaced `odom` or `base_link` frame leads to transform ambiguity and controller failure. In M2:
1. Every robot's `amr_gazebo.xacro` configures `<odom_frame>${robot_name}/odom</odom_frame>` and `<robot_base_frame>${robot_name}/base_footprint</robot_base_frame>`.
2. Every link in `amr_core.xacro` and `amr_lidar.xacro` is prefixed with `${robot_name}/` (`${robot_name}/base_link`, `${robot_name}/laser_frame`, `${robot_name}/front_caster`, `${robot_name}/rear_caster`).
3. `robot_state_publisher` runs inside the robot's namespace and resolves link parent/child transforms exclusively within its tree.
4. Dynamic odometry updates on `/tf` and latched static transforms on `/tf_static` do not conflict across robots.

### 7.3 Unique ROS 2 Node Names
To prevent node duplication warnings when spawning multiple robots:
- Spawner node: `Node(package='ros_gz_sim', executable='create', name=[robot_name, '_spawner'])`
- Bridge node: `Node(package='ros_gz_bridge', executable='parameter_bridge', name=[robot_name, '_bridge'])`
- State publisher: `Node(package='robot_state_publisher', executable='robot_state_publisher', namespace=robot_name)`
